Architecture Reference

Factory Inventory Management System

A single-page Vue 3 dashboard over a stateless FastAPI service that filters JSON fixtures held in memory. No database and no authentication. Almost everything is a read path from seven JSON files to seven screens; the sole write path is the Restocking tab, which appends submitted orders to an in-memory list.

Vue 3.4 + Vite 5 FastAPI + Pydantic v2 client :3000 api :8001 17 endpoints 7 JSON fixtures 40 backend tests 7 routes

Data Flow

The filter round-trip

The global FilterBar sits above router-view, so one set of four filters governs every screen. This is the request lifecycle when a user changes a dropdown.

  1. Selection mutates a shared ref FilterBar binds each <select> with v-model to a ref declared at module scope in useFilters.js. Because the refs live outside the useFilters() function body, every caller gets the same instance — the composable is a singleton store, not a factory.
  2. The active view's watcher fires Each view runs watch([selectedPeriod, selectedLocation, selectedCategory, selectedStatus], loadData). Only the mounted view reloads; the others re-run their watchers when next mounted.
  3. Filters are serialized to query params getCurrentFilters() returns { warehouse, category, status, month }, then api.js appends each to a URLSearchParams, omitting any value equal to "all". An absent param and "all" therefore mean the same thing on both sides of the wire.
  4. Parallel GET requests Views batch their reads with Promise.all — Dashboard.vue fetches summary, orders, inventory, and backlog in one wave.
  5. FastAPI filters Python lists in memory apply_filters() chains list comprehensions for warehouse, category, and status (the latter two compared case-insensitively). filter_by_month() then matches either a YYYY-MM prefix or expands a Q#-2025 key via QUARTER_MAP. Both use substring matching against order_date, not date parsing.
  6. Pydantic validates the response Typed routes declare response_model, so a JSON fixture that drifts from its model raises a server-side validation error rather than shipping a malformed payload.
  7. Raw data lands in refs; derived data is computed This is the load-bearing convention. Views store responses verbatim (allOrders, inventoryItems, summary) and express every aggregate as a computed — status counts, on-time delivery rate, average fulfillment days, category value rollups. Charts are hand-built SVG driven by those computeds.

Conventions Worth Preserving

Composables are module-scope singletons
useFilters and useI18n declare their refs outside the exported function. Moving a ref inside would silently convert the shared store into a per-component factory and break cross-view filtering.
Refs hold raw payloads; computed holds everything derived
No view stores an aggregate in a ref. Adding a metric means adding a computed, not another ref assigned inside loadData.
"all" is the client's sentinel, absence is the wire format
api.js strips "all" before the request; the server independently treats both a missing param and the literal string "all" as "no filter". Both halves of that contract have to stay in sync.
JSON shape and Pydantic model move together
Because routes declare response_model, editing a file under server/data/ without updating its model in main.py turns into a 500 at request time rather than a silent pass-through.
Charts are hand-written SVG
There is no charting dependency. Every bar, line, and donut is inline SVG bound to a computed property, styled with the slate palette (#0f172a, #64748b, #e2e8f0) and no emoji.

Drift Between Client and Server

These are gaps found while tracing the call graph, each verified against the running services rather than inferred. They are recorded here because they shape what the architecture actually does versus what the code implies.

Six client methods call routes that do not exist

api.js exposes getTasks, createTask, deleteTask, toggleTask, createPurchaseOrder, and getPurchaseOrderByBacklogItem. No /api/tasks or /api/purchase-orders route is registered in main.py — both return 404 against the live server. (The three restocking methods added alongside these do have routes.)

App.vue calls getTasks() on mount and wraps every task mutation in a try/catch that only console.errors, so the failure is invisible in the UI: the four hardcoded tasks from useAuth still render, and adding a task appears to do nothing.

Backlog.vue is unreachable
The view exists and fetches /api/backlog and /api/inventory, but it is absent from the route table in main.js and is not imported anywhere else. Backlog data surfaces only through the Dashboard's summary card and modal.
Purchase-order models are defined but never wired up
PurchaseOrder and CreatePurchaseOrderRequest are declared in main.py with no route using them, and purchase_orders.json is an empty array. The only live consumer is /api/backlog, whose has_purchase_order flag is therefore always false.
Dashboard renders a component that does not exist
Dashboard.vue:289 renders <PurchaseOrderModal>. There is no PurchaseOrderModal.vue in components/ and the name is not registered, so Vue logs "Failed to resolve component" on every Dashboard mount and renders nothing in its place. The "Create PO" buttons in the shortages table therefore do nothing — a fourth loose end from the same unfinished purchase-order feature.
Reports.vue bypasses the api.js seam
It imports axios directly and hardcodes http://localhost:8001/api/reports/… in two places. Everything else in the app routes through api.js, which is where a base-URL change would otherwise be a one-line edit.
Two independent quarter mappings
QUARTER_MAP drives filter_by_month(), while /api/reports/quarterly re-derives the same quarters with its own if/elif chain of substring checks. Both are hardcoded to 2025 and would need editing in tandem.
Some dashboard figures are constants, not data
Dashboard.vue hardcodes ordersData = { fulfilled: 187, goal: 200 } and fillRate = 96.8, and /api/dashboard/summary returns total_backlog_items from the unfiltered list — so that count does not move when filters change. The USD→JPY rate in currency.js is likewise a fixed 150.
